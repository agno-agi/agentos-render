## Measured improvement and retained coverage

The previous setup told users to attach a disk for AgentCore. That conflicts with
Render horizontal scaling and wrongly couples engineer recovery to the API host.
The implementation replaces this requirement with the existing S3CheckpointStore
and corrects the documentation used by OS Manager.

For `manager_explains_engineer_recovery`, the old image answered that AgentCore
required a persistent disk at `/data`. The corrected version explained that saved
PostgreSQL conversations do not reconstruct the engineer's working directory,
that optional AgentCore uses S3, and that recovery is from the last saved checkpoint.
The rubric and input were unchanged between those runs. Baseline failed;
candidate passed. This establishes the documented scenario, not general reliability.

A separate `manager_explains_simple_local_start` case tests the no-AWS quickstart
and direct-checkout boundary. Its first prompt asked for prerequisites while the
rubric also required an exact command and credential names. The answer omitted
those details. We retained that failed result and made the prompt request those
specifics; the rubric was not weakened. The recheck passed. This is a clarified
coverage case, not a measured application fix between those two attempts.

Both cases are retained in `evals/cases.py` with the `deployment` tag:

```sh
source .venv/bin/activate
python -m evals --tag deployment --json-output tmp/deployment-evals.json
```

The negative checkpoint test also rejects a tempting alternative: merely removing
the mount check while keeping disposable local archives would not provide durable
engineer recovery. Loss of the archive still prevents continuation. Local file
checkpoints remain explicitly limited; the hosted durable path uses S3.

## Limits and manual deployment checks

- No hosted Render, AWS IAM/S3 transfer, AgentCore execution or hosted sandbox
  recovery was exercised. Constructor checks are not AWS validation.
- Docker recovery used a deterministic fixture, not Claude/Codex in an isolated
  sandbox. Their successful direct API runs do not prove sandbox isolation.
  Codex's recovered namespace errors specifically do not prove enforcement of
  its inner namespace sandbox; the configured permission mode was unchanged.
- Local two-instance tests cover the paths listed above, not every timing failure,
  expired-lease race, rolling deployment, load level or exactly-once side effect.
- Browser OAuth, Render load balancing, arbitrary custom uploads/generated-file
  paths and remote engineer PR publication remain manual verification items.
- The default deployment stays at one API instance. Use the scaling guide and
  complete the relevant hosted checks before increasing it.
- Other templates remain unchanged; family parity is intentionally pending the
  accepted Render rollout. No claim of all-provider validation is made.

Use [the sandbox guide](../sandboxes.md) and [the scaling guide](../scaling.md)
for manual hosting. The [improvement guide](../improving.md) explains the retained
human-reviewed workflow; broader automated retrospectives are not enabled here.
